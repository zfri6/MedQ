# FPGA Intake Gate

默认策略：**只要用户提出的是 FPGA / RTL / Verilog / 仿真 / 波形 / 约束 / 上板 相关的工程任务，优先先走 `fpga-intake`。**

何时必须先 fpga-intake：
- 用户提出任何 FPGA/RTL/Verilog 相关工程请求，且有产出文件、修改代码、跑工具、定位错误、生成报告或交付物的意图
- 需求含混或缺少可执行边界，例如：
  - 没有说明要新建、修改、验证还是调试
  - 目标模块/功能不清楚，无法判断应调用哪个实现类 skill
  - 涉及板卡、引脚、约束、CDC、总线、寄存器语义、吞吐/延迟等关键工程条件，但缺少必要信息
  - 编译/仿真/波形/TD 综合问题没有提供可复现命令、日志、源文件或证据路径
  - 赛题要求交付文档/报告，但验收口径缺失

何时不要 fpga-intake（直接正常回复）：
- 用户在闲聊/科普/概念讨论，没有要产出文件、修改代码、跑工具或定位错误的意图。

允许 intake 快速放行的条件：
- 请求仍先进入 `fpga-intake`，但满足以下条件时不提问、直接产出 `doc/intake/summary.md` 并交接下一阶段：
  - 常见、独立、低上下文任务：计数器、分频器、移位寄存器、同步器、按键消抖、数码管扫描、简单 FSM、基础组合/时序数据通路、孤立 TB 生成、单点编译/仿真检查
  - 已给出足够的行为目标，能用合理默认端口、复位、模块名或标准工具流推进
  - 不涉及多模块架构拆分、协议初始化序列、CDC 策略、寄存器映射、复杂约束或板级集成
  - 未命中 `rules/00-skill-routing.md` 中"协议时序敏感模块判定标准"；命中且关键契约未冻结时，即使目标只有单模块 RTL，也不得走快速路径

稳定输入标准（满足越多，intake 越应该直接快速放行）：
- 明确目标与非目标
- 明确关键约束（接口/协议、时钟复位/CDC、吞吐/延迟、寄存器语义、工具链边界等与当前任务强相关的部分）
- 明确验收口径（PASS/FAIL、波形检查点、对标规则、TD 资源/时序目标、或可复现实验步骤）
- 提供必要证据：新开发给接口契约/需求来源/期望行为；修复编译给可复现命令与完整日志；上板问题给约束文件与 TD 报告

不满足快速放行条件时，仍应先 fpga-intake，并用最少问题补齐阻塞信息。

若后续 RTL 产出暴露出命中"协议时序敏感模块判定标准"的问题，且接口契约、协议边沿语义、阶段顺序、初始化步骤或命令/响应边界仍未冻结，不要把它视为"再试一次 RTL 就能解决"的同层问题；应回退到 intake/architecture/behavior-spec 层补齐上游定义后再继续。
